KNOWLEDGE NOTES

These are short casual answers to the five engineering questions. I kept them practical and
focused on how the ideas show up in a real AI product.

1. What is the difference between a REST API and MCP in the context of AI?

A REST API is just a normal web interface. You pick a URL, send a method like GET or POST, and get
back JSON. It is great when a service already exists and you want other programs to talk to it. The
hard part for AI is that the model does not know which endpoint to call, what the parameters mean,
or what the response looks like unless you tell it in the prompt or in your own code.

MCP stands for Model Context Protocol. It is a standard way for an AI client to discover and call
tools and read resources from a server. You describe a tool once with a name, a description, and a
JSON schema, and the client can expose it to the model. The model can then ask to call the tool and
the client handles the transport. MCP is more about giving the model a clean menu of capabilities
and keeping that menu in sync. REST is about exposing resources over HTTP.

So the simple version is this. REST is a transport and resource style that every backend already
speaks. MCP is an AI-facing contract that tells a model what it can do and how to do it. You can
put an MCP server on top of REST endpoints, and that is a very common pattern.

2. How can REST APIs and MCP improve an AI use case?

REST is how the AI gets real work done. The model should not guess a SQL query or hold your
business rules in its head. Give it an endpoint or a tool that does one safe thing, like fetch
receipts for a date range. That gives you validation, permissions, audit logs, and a stable place
to put transactions. When the model is wrong, the blast radius is small because the endpoint only
allows a known operation with checked inputs.

MCP improves the discovery and integration side. Instead of writing a custom prompt for every tool
and hardcoding it into every assistant, you publish tools once. A client can list them, see their
schemas, and let the model choose. This is nice when you have many tools or many assistants. It
also keeps the description of a tool next to the implementation, so the model sees the current
contract instead of an old prompt.

Used together they are pretty strong. REST owns the operations and data. MCP owns the model-facing
menu. You get reuse across clients without weakening the backend. The AI can chain a few narrow
tools, and each step is observable. That is much easier to debug than one giant prompt that tries
to do everything.

3. How do you make sure your AI agent answers correctly?

I do not trust the model with raw data access. I give it a few small tools with strict input
schemas and deterministic code behind them. The model picks a tool, my code validates the
arguments, runs the query, and returns rows plus a short summary. If the tool finds nothing, the
answer says there is no matching data instead of making something up.

Dates and money are the usual trouble spots. I normalize dates to ISO format before querying and I
store money as integer cents. I also tell the user which date range and filters were used. Every
answer carries evidence, so a person can check the rows behind it.

The next layer is testing. I test the tools directly with known fixtures, then I run end-to-end
tests over the UI and API. For the model path I keep a small evaluation set of real questions with
expected tool calls and expected numbers. If the prompt or model changes, the eval catches
regressions.

Finally I keep a human in the loop where it matters. Receipt OCR is reviewed before saving. The
query page shows the evidence and a confidence note. Logs record tool arguments and result counts.
And when no API key is present the app uses a deterministic router, so the core flow still works and
can be verified without a model.
